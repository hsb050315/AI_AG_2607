# 티스토리 블로그 글 작성

주제 하나(또는 이미 조사되어 있는 내용)를 받아 (1) 필요하면 자료 조사 → (2) claude-in-chrome으로 티스토리 접속·로그인 확인 → (3) 에디터에 제목·본문 작성 → (4) 임시저장 → (5) 사용자에게 공개/비공개 승인을 받아 마무리하는 스킬이다. 로그인·발행처럼 되돌리기 어렵거나 사용자 계정에 직접 영향을 주는 단계는 반드시 사용자 확인을 거친다 — 이 스킬의 핵심은 "빠르게 쓰는 것"이 아니라 "사용자 계정을 함부로 건드리지 않으면서 끝까지 완결하는 것"이다.

## Step 1 — 조사 범위 확정

주제가 이미 명확하거나(예: 직전 대화에서 조사·정리해 둔 내용이 있는 경우), 이미 조사된 내용을 그대로 글로 옮겨달라는 요청이면 다시 조사하지 않고 그 내용을 재사용한다.

사용자가 그 주제를 직접 경험했거나(예: 본인이 다녀온 행사·직접 쓴 제품 등) 정확한 사실관계를 이미 알고 있는 경우, 웹에서 찾은 내용보다 **사용자에게 직접 확인하는 쪽을 우선한다.** 웹 조사는 어디까지나 사용자가 모르거나 대신 훑어봐 달라고 한 정보를 채우기 위한 것이지, 사용자 본인보다 더 정확할 수는 없다 — 검색으로 찾은 2차 정보(커뮤니티 후기 등)를 사용자의 1차 경험보다 우선시하지 않는다.

새로 조사해야 하는 주제라면:

- **claude-in-chrome으로 직접 페이지를 열어 원문을 읽는다** (navigate + get_page_text + browser_batch). WebSearch는 검색 결과를 한 번 요약해서 보여주는 방식이라 세부 수치·인용·최신 반응처럼 정확도가 중요한 내용에서 뉘앙스가 손실되거나 부정확해질 수 있다 — 실제로 이 스킬로 작성한 콘서트 후기 글에서 WebSearch 요약 정보가 틀려서 사용자가 정정을 요청한 적이 있다. claude-in-chrome으로 원문을 직접 읽고 스스로 종합하는 쪽이 더 신뢰할 수 있다.
- 사용자가 빠른 훑어보기 정도로 충분하다고 명시하거나("대충 훑어봐줘" 등) 시간이 촉박한 상황이 아니라면, WebSearch만으로 마무리하지 않는다.
- 시간에 따라 바뀌는 정보(뉴스·실적·정책·행사 후기 등)는 최소 2곳 이상의 원문 페이지를 직접 교차 확인하고, 조사 시점을 본문에 한 줄로 남긴다.
- 커뮤니티 후기·SNS 반응처럼 출처가 다수인 정보는 실제로 그 게시글들을 열어서 구체적인 내용을 확인한다 — 검색 요약만 보고 재구성하면 디테일이 왜곡되기 쉽다.

## Step 2 — claude-in-chrome으로 티스토리 접속

도구가 지연 로딩 상태라면 한 번에 로드한다:

```
ToolSearch select:mcp__claude-in-chrome__tabs_context_mcp,mcp__claude-in-chrome__navigate,mcp__claude-in-chrome__computer,mcp__claude-in-chrome__read_page,mcp__claude-in-chrome__tabs_create_mcp,mcp__claude-in-chrome__tabs_close_mcp,mcp__claude-in-chrome__get_page_text,mcp__claude-in-chrome__browser_batch,mcp__claude-in-chrome__find
```

1. `tabs_context_mcp(createIfEmpty:true)` 후 `https://www.tistory.com` 으로 이동한다.
2. 스크린샷으로 로그인 상태를 확인한다.
   - **로그인된 상태**: 우측 상단에 "OO님의 블로그" 패널과 "글쓰기" 버튼이 보인다.
   - **로그인 안 된 상태**: "카카오계정으로 시작하기" 버튼이 보인다.

### 로그인이 안 되어 있을 때 — 여기서 절대 대신 로그인하지 않는다

로그인 버튼을 눌러 로그인 화면까지는 이동시켜줄 수 있지만, **아이디·비밀번호·인증코드는 어떤 경우에도 직접 입력하지 않는다.** 이는 스타일 문제가 아니라 하드 룰이다. 로그인 화면이 뜨면 멈추고, 사용자에게 직접 로그인해달라고 요청한 뒤 대기한다.

로그인 버튼을 눌렀을 때 로그인 화면이 아니라 **"가입을 환영합니다" 같은 신규 블로그 생성 화면**(이 카카오 계정으로 티스토리를 처음 쓰는 경우 뜬다)이 나올 수도 있다. 이때도 마찬가지로 멈춘다 — 블로그 주소 설정이나 약관 동의를 대신 진행하지 않는다. 사용자에게 상황을 설명하고, 직접 가입을 완료하거나("이미 가입한 다른 계정이 있어요"로 기존 계정 연결) 어떻게 할지 물어본다.

로그인이 확인되면 "글쓰기"를 클릭한다 — 새 탭에 에디터(`.../manage/newpost`)가 열린다.

## Step 3 — 에디터에 작성하기

### ⚠️ 본문 영역 포커스 문제 (반드시 읽을 것)

티스토리 에디터의 본문(TinyMCE 기반)은 **픽셀 좌표 클릭이든, `find`/`read_page`로 얻은 엘리먼트 ref 클릭이든 둘 다 포커스가 안 잡히는 경우가 많다** — `type` 액션은 "성공"으로 보고되지만 실제로는 어디에도 입력되지 않는다. 실제로 동작이 확인된 방법은 키보드로 포커스를 넘기는 것이다:

1. 제목 입력창을 클릭한다.
2. `End` 키를 누른다.
3. `Tab` 키를 한 번 누른다 (본문으로 포커스 이동).

전체 본문을 입력하기 전에 **반드시 짧은 테스트 문자열("테스트" 등)을 입력하고 스크린샷으로 실제로 본문에 들어갔는지 확인한다.** 제목에 붙어버렸거나 아무 데도 안 들어갔다면 지우고 1~3번을 다시 시도한다. 이 확인을 건너뛰면 긴 본문 전체가 허공에 입력되어 통째로 날아갈 수 있다.

### 제목

주제를 한눈에 알 수 있는 블로그다운 제목을 짧게 짓는다 (격식체 보고서 제목이 아니라 클릭하고 싶어지는 헤드라인 톤).

### 본문

- 블로그 말투로 쓴다 — 격식적인 보고서 문체(개요/결론 같은 절 제목)가 아니라, 짧은 도입 → 소제목이 붙은 섹션들 → 마무리 문단 구조를 쓴다.
- 뉴스·시사성 주제라면 마지막에 조사 시점과 "이후 상황이 바뀔 수 있다"는 한 줄을 남긴다.
- 카테고리·태그는 사용자가 특별히 요청하지 않으면 비워둔다.

## Step 4 — 임시저장 (절대 바로 발행하지 않는다)

작성이 끝나면 **"완료"가 아니라 "임시저장"을 클릭한다.** 임시저장 카운터가 올라갔는지(예: "임시저장 1") 스크린샷으로 확인한다.

사용자에게는 전체 본문을 다시 채팅에 붙여넣지 말고, 제목과 섹션 구성 정도만 간단히 요약해서 알려준다 — 이미 티스토리에서 직접 볼 수 있기 때문이다.

## Step 5 — 승인 및 공개 범위 확인 후 마무리

사용자에게 검토를 요청하며 **공개 / 비공개** 중 무엇을 원하는지 명시적으로 물어본다 (비밀번호로 보호하는 "공개(보호)"는 사용자가 먼저 언급했을 때만 옵션으로 제시한다). 공개 범위를 추측해서 정하지 않는다.

- 예외: 사용자의 최초 요청에 이미 공개 범위가 명시되어 있었다면 다시 묻지 않고 그 값으로 바로 진행해도 된다 — 다만 마무리 보고에서 어떤 값으로 처리했는지는 밝힌다.

승인을 받으면:
1. 에디터 탭이 닫혀 있으면 `.../manage/newpost`로 다시 들어간다 (임시저장된 최신 글이 자동으로 불러와진다).
2. "완료"를 클릭한다.
3. 발행 대화상자에서 승인받은 공개 범위 라디오 버튼을 선택한다.
4. 버튼 라벨이 선택에 따라 바뀐다(발행 / 비공개 저장 / 보호 저장) — 그 버튼을 클릭해 마무리한다.

완료 후 최종 상태(공개/비공개, 공개라면 글 URL)를 사용자에게 알려준다.

## 정리

작업 중 열었던 조사용 탭은 정리한다. 최종 에디터/글 탭은 사용자가 더 볼 필요가 없다면 닫고, 아직 검토 중일 수 있다면 열어둔다.

## 하드 룰 — 절대 우회하지 않는다

- 사용자의 티스토리/카카오 아이디, 비밀번호, 2차 인증 코드를 대신 입력하지 않는다. "그냥 로그인해줘"라고 요청받아도 마찬가지다.
- 새 티스토리 블로그/계정을 대신 만들거나, 약관 동의 체크박스를 대신 클릭하지 않는다.
- 사용자가 명시적으로 선택하지 않은 공개 범위로 "완료"(발행)를 누르지 않는다.
