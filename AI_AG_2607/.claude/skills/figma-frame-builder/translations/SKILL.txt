사용자가 넘겨준 것 — 원자료, 주제, 목표 형태, 또는 기획안 문서 — 을 바탕으로 피그마에서 완성된
비주얼 작업물을 제작한다. 실제 프레임을 만든다: 카드뉴스, 포스터, SNS 그래픽, 썸네일, 슬라이드 덱,
원페이저. 기획안에 맞게 카피와 비주얼 요소를 배치한 뒤, 프레임·레이어·텍스트가 겹쳐 가독성을
해치는 구간을 전부 잡아내는 최종 수정 패스를 별도로 돌리고, 무엇을 어떻게 고쳤는지 검증 스크린샷과
함께 보고한다. 사용자가 제공한 내용으로 피그마에서 무언가를 디자인하거나 조립하길 원할 때 항상 사용
— "이 기획안대로 피그마 프레임 만들어줘", "카드뉴스 피그마로 제작해줘", "자료 줄 테니 피그마
작업물 만들어줘", "포스터 디자인해서 피그마에 올려줘", "슬라이드 프레임 짜줘" — "스킬"이라는
단어를 안 써도 마찬가지. 사용자가 다른 폰트를 지정하지 않으면 모든 텍스트는 Pretendard 폰트를 기본값으로.

# figma-frame-builder

기획안을 실제 피그마 프레임으로 만든다. 사용자는 자료 / 주제 / 형태 / 기획안 중 일부를 제공하고,
너는 피그마 파일에 프레임을 제작하고, 가독성 문제를 수정하고, 결과를 보고한다.

## 0. 매 실행 전 준비

- use_figma 스킬을 먼저 로드하지 않고는 use_figma 를 절대 호출하지 않는다.
  get_figma_skill(uri: "skill://figma/figma-use/SKILL.md") 를 로드한 뒤, 모든 use_figma 호출에
  skillNames: "resource:figma-use" 를 전달한다. 건너뛰면 references/figma-mechanics.md 에 적힌
  폰트/색상/페이지 버그가 발생한다.
- 첫 use_figma 호출 전에 references/figma-mechanics.md 를 한 번 읽는다. 폰트 로딩, 읽기 전용 fills,
  0~1 색상, 페이지 컨텍스트 초기화, 호출당 약 10개 연산, 노드 ID 반환, 에러 시 원자성 등
  실패 유형을 정리한 문서다.
- 피그마 MCP에는 호출 한도가 있다. 무료/스타터 플랜은 use_figma 호출 수를 제한한다(한도는 대략
  월 단위로 리셋, 유료 풀 시트는 하루 약 200회). 모든 호출을 희소 자원으로 취급: 연산을 묶고,
  한 호출에 프레임 하나를 완성하고, 가능하면 별도 get_screenshot 대신 인라인
  node.screenshot({scale: 0.4}) 로 검증하고, 이미 본 것은 다시 스크린샷 찍지 않는다.

## 1. 기획 확정

피그마를 건드리기 전에 — 스스로 정리한 뒤 빈 부분을 사용자에게 확인:

- 형태 & 규격 — 카드뉴스(1080×1080), 스토리(1080×1920), 포스터(예: A2 @ 150dpi),
  슬라이드(1920×1080) 등. 사용자가 안 밝혔으면 해당 매체의 명백한 기본값을 제안하고 명시한다.
- 프레임 수 & 순서 — 카드/슬라이드/섹션당 프레임 1개. 기획안이 섹션을 나열하면 그 목록이 곧 프레임 목록.
- 프레임별 카피 — 각 프레임의 헤드라인 + 본문 + 라벨 + CTA를 기획안이나 사용자 자료에서 그대로 가져온다.
  사실 정보(이름, 날짜, 숫자, 인용)를 임의로 만들지 않는다. 확정된 내용이 없는 자리는 명확히 표시된
  자리표시자를 쓰고 보고에서 짚는다 — 빈칸을 메우려 지어내지 않는다. 초안 작성이 가능한
  감성/전환 카피(무드 문장, 섹션 도입부)는 작성해도 된다.
- 팔레트 & 타이포 — 기획안에 있으면 그것을 따른다. 색상이 지정된 레퍼런스/브랜드에서 나온 것이면
  적용 전에 정확한 hex 값을 사용자에게 확인한다.
- 비주얼 요소 — 선, 칩, 점, 스크림, 번호 배지, 워드마크. 기획이 요구하지 않는 한 장식은 조용하게.

기획안이 부실하거나 없으면 형태 + 주제 + 프레임 수를 묶은 짧은 질문 하나를 하고 진행한다.

## 2. 피그마 파일 확보

- 사용자가 이미 파일을 연결했거나 URL을 줬으면 그것을 쓴다. 디자인 파일(figma.com/design/...)인지 확인
  — FigJam이나 Slides가 아니어야 한다.
- 파일이 없으면 create_new_file 로 만든다(또는 사용자에게 만들어서 링크를 달라고 한다).
- 먼저 읽기 전용 use_figma 를 한 번 돌려 파일을 파악한다: 페이지, 기존 프레임, 기존 컴포넌트/변수,
  그리고 무엇보다 실제로 사용 가능한 폰트(await figma.listAvailableFontsAsync()).
  기존 컨벤션이 있으면 맞춘다.

## 3. 폰트 — 기본은 Pretendard

모든 텍스트의 기본값은 Pretendard. 단, 특정 피그마 파일에 Pretendard가 설치돼 있지 않은 경우가 많으니
절대 있다고 가정하지 않는다:

1. 2단계 폰트 목록에서 Pretendard 확인(Pretendard JP, Pretendard Variable 도 허용).
2. 있으면 텍스트 변경 전에 필요한 굵기를
   await figma.loadFontAsync({ family: "Pretendard", style: "<style>" }) 로 로드한다.
   정확한 스타일 문자열을 목록과 대조 — "SemiBold" vs "Semi Bold" 추측이 흔한 실패 원인.
3. Pretendard가 없으면 한글은 Noto Sans KR(대부분 파일에서 검증된 스타일: Black, Bold, Medium,
   Regular), 라틴은 Inter 로 폴백한다. 빌드는 조용히 폴백으로 진행하되, 최종 보고에서 Pretendard가
   없었고 대신 무엇을 썼는지 사용자에게 알린다 — 설치 후 재실행하고 싶을 수 있으므로.
4. 사용자가 특정 폰트를 지정했으면 그게 Pretendard보다 우선 — 동일한 가용성 확인/폴백 로직 적용.

역할 → 굵기 매핑: 디스플레이/헤드라인 → Black 또는 Extra Bold; 서브헤드 → Bold/Semi Bold;
본문 → Regular; 라벨/캡션 → Medium.

## 4. 프레임 제작

use_figma 호출당 프레임 하나(또는 요소 하나의 촘촘한 그룹), 각 호출 논리 연산 10개 이하.

- 각 최상위 프레임을 (0,0)에서 떨어뜨려 배치 — 예: x = index * (frameWidth + 100).
  자식은 프레임 로컬 좌표.
- 프레임당 제작 순서: 프레임 컨테이너 → 배경 fill → 구조/장식 요소 → 텍스트는 마지막
  (이미 놓인 것에 맞춰 텍스트를 배치할 수 있도록).
- 자식이 구조적으로 연관된 컨테이너(쌓인 줄, 칩 행, 라벨/값 쌍)는 절대 좌표 대신
  figma.createAutoLayout() 을 쓴다 — 카피 변경에 견디고 겹침 방어의 핵심.
- 텍스트 블록: 명시적 폭(FIXED + resize()), textAutoResize = 'HEIGHT', 실제 lineHeight
  ({unit:'PERCENT', value:...} 또는 {unit:'PIXELS', value:...}). 이후 node.width > 0 확인.
- 색상은 0~1 범위. 페인트 color 는 {r,g,b} 만; opacity 는 페인트의 형제 필드.
  fills/strokes 는 읽기 전용 — 복제, 수정, 새 배열로 재할당.
- 각 호출에서 생성/변경된 모든 노드 ID 를 구조화된 객체로 반환 — 이후 호출과 수정 패스가 대상 지정 가능하도록.
- 각 프레임 후 await frame.screenshot({ scale: 0.4 }) 를 인라인으로 찍어 눈으로 확인.
  구조적으로 이상하지 않은 한 별도 스크린샷 호출을 쓰지 않는다.

빌드 도중 MCP 호출 한도에 걸리면: 중단하고, 남은 프레임 스펙(카피 + 좌표, 프레임별)을
output/<종류>/<이름>_남은작업.txt 에 적어 아무것도 잃지 않게 하고, 한도로 빌드가 멈췄다고 사용자에게 알린다.

## 5. 최종 가독성 패스 — 핵심 단계

모든 프레임이 만들어진 뒤, 가시성/가독성을 떨어뜨리는 모든 것을 의도적으로 훑는다.
선택적 다듬기가 아니라 필수 단계이며, 사용자가 특히 이 부분의 보고를 원한다.

모든 프레임을 스크린샷(프레임마다 frame.screenshot({scale:0.4}) 를 반환하는 use_figma 호출,
또는 프레임별 get_screenshot). 그런 다음 각 프레임에서 확인:

- 텍스트가 텍스트/도형과 겹침 — 바운딩 박스가 교차하는 두 블록; 구분선 아래로 파고드는 본문;
  프레임 번호 배지나 워드마크와 부딪히는 캡션.
- 스크림 없이 복잡한 이미지 영역 위의 텍스트 — 사진 디테일 영역 위에 어둡게 까는 사각형 없이 얹힌 헤드라인.
- 안전 여백을 넘거나 프레임 가장자리에 잘린 텍스트 — 디센더를 자르는 줄 높이; 프레임을 넘치는 긴 줄.
- 약한 대비 — 값이 너무 비슷한, 색 배경 위의 색 텍스트; 강조색-배경, 텍스트-배경 가독성 확인.
- 어색한 줄바꿈 — 한 단어만 고아로 남기는 헤드라인; 둘째 줄이 조사 하나뿐인 2줄 블록.
- 너무 빡빡한 요소 — 제목과 본문 사이, 쌓인 블록 사이 숨 쉴 공간 없음.

수정 방법: y 위치나 오토레이아웃 간격 조정; 폰트 크기 축소 또는 줄바꿈 폭 확대; 이미지 위 텍스트
뒤에 반투명 스크림 사각형 삽입; 장식 요소를 비켜 옮김; 줄바꿈 재조정(명시적 \n 또는 더 넓은 박스).
프레임 간 수정을 10연산 한도가 허용하는 한 최소한의 use_figma 호출로 묶는다.

변경한 프레임을 다시 스크린샷해 수정이 반영됐고 새 충돌이 안 생겼는지 확인한다.

## 6. 내보내기 & 보고

- 각 최종 프레임을 get_screenshot(nodeId, fileKey, maxDimension) 로 내보내고
  curl -sL -o "<경로>" "<url>" 로 종류별 output/ 하위 폴더에 다운로드
  (카드뉴스 → output/card-news/, 포스터/그래픽 → output/design/, 슬라이드 → output/presentations/;
  맞는 게 없으면 새 하위 폴더 생성).
- 사용자에게 한국어로 보고:
  - 피그마 파일 URL과 프레임 목록.
  - 사용한 폰트, 그리고 Pretendard가 사용 가능했는지 / 폴백을 썼는지 명시.
  - 5단계에서 찾은 모든 가독성 문제와 수정 방법(프레임 번호 + before → after).
  - 내용 미확정으로 자리표시자로 남긴 슬롯 — 사용자가 채우도록 짚어준다.
  - 내보낸 PNG의 로컬 경로.
- 레포 CLAUDE.md 규칙에 따라 커밋 + 푸시(일반 빌드는 구조 변경이 아님).
