## Git workflow (깃 작업 흐름)

- 저장소: https://github.com/hsb050315/AI_AG_2607
- 사용자가 "클론해줘"라고 말하면 이 저장소를 클론한다.
- 사용자가 요청한 작업이 끝나면 기본적으로 승인 없이 자동으로 커밋·푸시한다.
- 예외: 변경 규모가 커서 파일/폴더 구조 자체를 재구성하거나, 프로젝트의 다른 부분과 서로 간섭·영향을 주는 경우에는 커밋·푸시 전에 계획을 제시하고 명시적 승인을 받는다.

## Markdown file conventions (마크다운 파일 규칙)

- `.md` 파일을 새로 작성하거나 수정할 때는 내용을 영어로 작성한다.
- `.md` 파일은 영어로 유지한다. 추가로 한국어 번역본을 `.txt` 파일로 생성하여, 원본 `.md` 파일과 같은 위치가 아닌 별도의 새 폴더에 저장한다 — 예: `docs/foo.md` → `translations/foo.txt`.
- `.md` 파일이 수정되면 동일한 이름의 번역본 `.txt` 파일도 함께 갱신한다.

## Task workflow (작업 흐름)

- 기본은 자율적으로 진행한다: 규모가 작고 영향 범위가 제한적인 변경(일반적인 수정, 추가, 단일 파일 작업 등)은 승인을 먼저 구하지 않고 바로 진행한다.
- 계획 제시 + 명시적 승인(예: "yes", "진행", "ok")은 규모가 크거나 영향이 큰 작업에만 요구한다 — 예: 파일/폴더 구조를 재구성하거나, 프로젝트의 여러 다른 부분에 간섭·영향을 주는 변경. 이런 경우에는 짧은 번호 매긴 단계 목록을 채팅 답변에 작성한 뒤 멈추고 승인을 기다린다. 응답이 없거나 모호한 답변에는 진행하지 않는다.
- 여러 단계로 이루어진 작업의 진행 상황은 할 일 목록 도구(TaskCreate/TaskUpdate)로 추적하되, 그럴 만큼 작업이 충분히 중요할 때만 사용한다 — 사소한 동작 하나하나까지 할 일 항목으로 만들 필요는 없다.
- 순수 대화형/정보 제공 답변, 그리고 파일이나 저장소 상태를 바꾸지 않는 조회성 확인(예: 파일 읽기, `git status`, `git log`, `git diff`)에는 이 절차가 전혀 적용되지 않는다.

## Output folder conventions (산출물 폴더 규칙)

- 작업 산출물은 모두 종류별로 `output/` 하위에 정리한다:
  - 보고서(docx/txt 쌍) → `output/reports/`
  - 리서치 스프레드시트(xlsx) → `output/research/`
  - 스크린샷 → `output/screenshots/`
  - Playwright MCP를 활용해 산출되는 결과물(브라우저 스크린샷, 페이지 캡처 등) → `output/playwright/`
- 기존 하위 폴더에 맞지 않는 새로운 종류의 산출물이 생기면, 프로젝트 루트에 그대로 두지 말고 `output/` 하위에 새 폴더를 만들어 정리한다.
