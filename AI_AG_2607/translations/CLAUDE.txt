- 예외: 변경 규모가 커서 파일/폴더 구조 자체를 재구성하거나, 프로젝트의 다른 부분과 서로 간섭·영향을 주는 경우에는 커밋·푸시 전에 계획을 제시하고 명시적 승인을 받는다.

## Markdown file conventions (마크다운 파일 규칙)

- `.md` 파일을 새로 작성하거나 수정할 때는 내용을 영어로 작성한다.
- `.md` 파일은 영어로 유지한다. 추가로 한국어 번역본을 `.txt` 파일로 생성하여, 원본 `.md` 파일과 같은 위치가 아닌 별도의 새 폴더에 저장한다 — 예: `docs/foo.md` → `translations/foo.txt`.
- `.md` 파일이 수정되면 동일한 이름의 번역본 `.txt` 파일도 함께 갱신한다.

## Task workflow (작업 흐름)

- 작업을 시작하기 전에 먼저 할 일 목록(TaskCreate 사용)으로 단계를 나누어 사용자에게 보여준다 — 아무리 작은 작업이라도 예외 없이 적용한다.
- 계획 제시 + 명시적 승인(예: "yes", "진행", "ok")은 규모가 크거나 영향이 큰 작업에만 요구한다 — 예: 파일/폴더 구조를 재구성하거나, 프로젝트의 여러 다른 부분에 간섭·영향을 주는 변경. 이런 경우에는 실행하기 전에 승인을 기다린다. 응답이 없거나 모호한 답변에는 진행하지 않는다. 규모가 작고 영향 범위가 제한적인 변경(일반적인 수정, 추가, 단일 파일 작업 등)은 할 일 목록을 보여준 뒤 별도의 승인을 기다리지 않고 바로 진행해도 된다.
- 작업이 진행되는 동안에는 할 일 목록을 계속 최신 상태로 눈에 보이게 유지한다 — 각 항목의 상태(진행 중/완료)를 TaskUpdate로 갱신해서, 사용자가 현재 무엇이 진행 중인지 항상 볼 수 있게 한다.
- 순수 대화형/정보 제공 답변, 그리고 파일이나 저장소 상태를 바꾸지 않는 조회성 확인(예: 파일 읽기, `git status`, `git log`, `git diff`)에는 이 절차가 전혀 적용되지 않는다.

## Memo classification and routing (메모 분류 및 저장 규칙)

- 사용자가 메모나 파일을 전송하면 아래 규칙에 따라 분류하고, 해당하는 스킬을 실행해 Notion에 저장한다. 메모 자체가 요청이므로 이 분류·저장은 자동으로 수행한다.
- **개인**: `개인:` 으로 시작하거나, 개인 / 친구 / 가족 등의 키워드가 들어 있으면 → `notion-personal` 스킬 실행 → "개인 일정" DB에 저장.
- **업무**: `업무:` 로 시작하거나, 업무 / 과제 등의 키워드가 들어 있으면 → `notion-work` 스킬 실행 → "업무" DB에 저장.
- **학습**: `학습:` 또는 `배움:` 으로 시작하거나, 자료조사 / 공부 / 강의 등의 키워드가 들어 있으면 → `notion-study` 스킬 실행 → "학습" DB에 저장.
- **완료**: `완료:` 로 시작하거나, 마무리 / 제출 / 완료 등의 키워드가 들어 있으면 → `notion-complete` 스킬 실행 → "완료작업" DB에 저장.
- 우선순위: 맨 앞의 명시적 접두어(`개인:` / `업무:` / `학습:` / `배움:` / `완료:`)가 키워드 일치보다 항상 우선한다. 접두어가 없고 키워드가 여러 분류를 가리키거나, 아무 규칙에도 맞지 않으면 추측하지 말고 저장 전에 어느 분류인지 사용자에게 물어본다.

## Skill creation (스킬 생성)

- 새 스킬을 만들어 달라는 요청을 받으면(skill-creator 스킬이 실행되는 경우 포함), 한 번의 효율적인 흐름으로 만든다: 요구사항을 수집하고 `SKILL.md`와 필요한 보조 파일을 작성한 뒤 마친다.
- 최초 생성 시에는 테스트하지 않는다 — eval, 벤치마크, 분산 분석, 시험 실행, 테스트/검증 서브에이전트 모두 하지 않는다. 사용자가 명시적으로 테스트를 요청하지 않는 한 skill-creator의 테스트·벤치마크 단계는 전부 건너뛴다.
- 컨텍스트가 비대해지지 않고 자동 컴팩트가 발생하지 않도록 과정을 가볍게 유지한다: 필요한 것만 읽고, 큰 참고 파일을 다시 읽지 않으며, 불필요한 전체 파일 내용을 출력하지 않고, 전체 파일 읽기보다 필요한 부분만 읽는 방식을 우선한다.
- 파일 작성이 끝나면 무엇을 만들었는지 짧게 요약하고 사용자가 직접 써 보게 한다. 사용자가 문제를 보고하거나 요청할 때만 반복·테스트한다.

## Output folder conventions (산출물 폴더 규칙)

- 작업 산출물은 모두 종류별로 `output/` 하위에 정리한다:
  - 보고서(docx/txt 쌍) → `output/reports/`
  - 리서치 스프레드시트(xlsx) → `output/research/`
  - 스크린샷(Playwright MCP로 캡처한 브라우저 스크린샷·페이지 캡처 포함) → `output/screenshots/`
  - 디자인/템플릿 검색 결과물(예: Canva 템플릿 검색·상세 페이지 스크린샷) → `output/references/image/`
- 기존 하위 폴더에 맞지 않는 새로운 종류의 산출물이 생기면, 프로젝트 루트에 그대로 두지 말고 `output/` 하위에 새 폴더를 만들어 정리한다.
