# design-concept: 리서치 기반 비주얼 디자인 컨셉

주제 하나를 받아 "이것에 대해 아직 아무것도 모른다" 상태에서 "팀 누구나 이걸 기준으로 만들 수 있는, 문서화된 비주얼 방향이 여기 있다" 상태까지 끝까지 끌고 간다. 두 단계, 순서대로:

1. 주제를 제대로 **조사**한다 (기존 지식이 아니라 웹 조사).
2. 조사가 실제로 말하는 내용으로부터 디자인 컨셉을 **도출**한다 — 무드/톤 키워드, 컬러 팔레트, 타이포그래피 — 그리고 사용자의 Drive에 Google Docs 문서로 정리한다.

이 컨셉은 의도적으로 매체 중립적이다. 결과물이 나중에 웹사이트가 되든, 덱이 되든, 카드뉴스가 되든, Canva 디자인이 되든 쓸 수 있어야 하므로, 레이아웃이나 컴포넌트 스펙이 아니라 방향(팔레트, 타이포, 무드) 수준으로 권고를 유지한다.

## 흐름

### 1. 주제 범위 확정

요청에서 주제가 충분히 명확하면 바로 시작한다. 대상이 정말 모호할 때만(예: 여러 회사일 수 있는 브랜드명) 짧게 되묻는다. 애매하지만 합리적으로 판단 가능하면, 그 가정을 문서의 "근거 및 출처" 섹션에 적어두고 진행한다.

사용자가 말하지 않았다면 빠르게 짚어두면 좋은 것: 의도한 타깃 독자, 시장/지역, 이미 염두에 둔 감정적 목표가 있는가? 이것들은 컨셉을 날카롭게 하지만 진행을 막는 요소는 아니다.

### 2. 심층 조사

이 작업은 **조사관 서브에이전트**를 스폰하는 것을 선호한다 — 출처가 잘 갖춰진 한국어 리서치에 특화되어 있고 조사 컨텍스트를 메인 스레드 밖에 둔다. 다음을 다루는 집중된 브리프를 준다:

- **분야 개요** — 이 주제/산업이 실제로 무엇이고 현재 상태는 어떤가
- **타깃** — 독자 또는 고객이 누구인가; 그들의 기대, 연령대, 사용 맥락
- **경쟁·유사 사례의 비주얼 경향** — 비교 가능한 브랜드/제품이 스스로를 어떻게 표현하는가(색, 타이포, 이미지 무드); 카테고리 관행과 그것을 깨는 지점
- **색·타이포 관습과 연상** — 이 분야와 관습적으로 연결되는 색과 타이포 스타일, 그것이 담는 감정/연상(한국 시장 등 문화별 차이 반영)
- **전달하려는 감정·가치** — 이 주제가 전달해야 할 느낌이나 브랜드 가치
- **최근 트렌드** — 이 영역의 디자인 방식에서 최근의 변화

현재 컨텍스트에서 서브에이전트 스폰이 불가능하면, 같은 브리프를 기준으로 WebSearch/WebFetch로 직접 조사한다. 어느 쪽이든: 구체적인 내용은 2개 이상 출처로 교차 확인하고, 출처 URL을 남기고, 오늘 날짜를 조사 시점으로 기록한다.

### 3. 컨셉 도출

조사를 세 가지 산출물로 종합한다. 모든 선택은 조사가 말한 무언가로 거슬러 올라갈 수 있어야 한다 — 색이나 폰트가 왜 맞는지 조사로부터 설명할 수 없다면 그것은 추측이고, 추측은 팔레트가 아니라 "근거 및 출처"에 열린 질문으로 들어간다.

**무드 · 톤앤매너 키워드 (3~5개)**
- 의도한 느낌을 담는 컨셉 키워드 3~5개 (예: "절제된 신뢰감", "따뜻한 실용주의", "선명한 에너지").
- 각각에 대해: 여기서 무엇을 뜻하는지 한 줄, 그리고 시각적으로 어떻게 나타나야 하는지(굵기, 대비, 채도, 여백감).
- 이들을 묶는 "컨셉 스테이트먼트" 한 문장 — 컨셉을 기준으로 만드는 누구에게나 북극성이 되는 문장.

**컬러 팔레트**
- 다음 역할을 커버한다: 주조색(dominant), 보조색(secondary, 1~2개), 강조색(accent), 중립색(neutral/배경/텍스트).
- 각 색에 필요한 것: 색상명, 역할, HEX, 사용처, 선정 근거(왜 — 조사와 연결).
- 대략적인 사용 비율을 준다 (예: 주조 60 / 보조 25 / 강조 10 / 중립은 배경·텍스트).
- 중립 배경 위의 강조색, 배경 위의 텍스트 색이 읽힐 만큼 대비가 충분한지 확인한다.

**타이포그래피**
- 제목용 페어링과 본문용 페어링을 각각 추천하고, 각각 **한글 폰트 + 영문 폰트**를 포함한다 (한글은 보통 라틴과 다른 패밀리가 필요하다).
- 컨셉이 분명히 개성 있는 폰트를 요구하지 않는 한, 널리 쓰이고 무료인 폰트를 선호한다 (한글: Pretendard, Noto Sans KR, 나눔, Gmarket Sans, SUIT; 라틴: Inter, Roboto, Source Serif 등).
- 각각에 대해: 무드에 왜 맞는지(글자꼴 성격, 굵기 범위), 그리고 대체 폰트.

### 4. 문서 작성 전 사용자에게 컨셉 제시

팔레트(HEX 포함), 키워드, 폰트 선택을 채팅으로 보여주고, 승인 또는 수정을 요청한다. 사용자가 보지 않은 비주얼 방향 — 특히 색 — 을 적용하면 빗나가기 쉽다; 여기서 30초 확인이 재작업을 막는다. 피드백을 반영해 조정한 뒤 다음으로 넘어간다.

### 5. Drive 폴더 확인 — 반드시 매번

이 단계는 목적지가 아무리 뻔해 보여도 절대 건너뛰지 않는다.

- `find_folders(name_query)`를 사용자가 언급한 폴더명 또는 주제 키워드로 호출하고, 후보를 보여준 뒤 어느 것인지 확인받는다.
- 사용자가 폴더를 말하지 않았으면 물어본다: "어느 폴더에 저장할까요? (비워두면 내 드라이브 최상위에 만듭니다)"
- 폴더 없음 → `create_document(title, folder_id=None)` (내 드라이브 최상위).
- `create_document`가 `insufficientParentPermissions`로 실패 → 그 폴더는 사용자 소유가 아니다(열람 전용 공유). 그 사실을 알리고, 폴더나 최상위를 다시 묻는다.

### 6. Google 문서 조립

`gws-doc` 스킬의 빌더를 재사용한다 — `gws` 호출이나 Docs API JSON을 직접 짜지 않는다. 표/인덱스 계산은 거기서 이미 처리된다.

```python
import sys, glob
# 빌더 위치 찾기 (레포 구조: .claude/skills/gws-doc/scripts/gws_docs_builder.py)
builder_dir = glob.glob("**/skills/gws-doc/scripts", recursive=True)[0]
sys.path.insert(0, builder_dir)
from gws_docs_builder import (
    find_folders, create_document, get_share_link,
    add_title, add_subtitle, add_heading, add_paragraph,
    add_emphasized_paragraph, add_bullet_list, add_table,
)

folders = find_folders("브랜드")          # 사용자가 폴더 확인해준 뒤
doc_id = create_document("OO 디자인 컨셉", folder_id=folders[0]["id"])  # 또는 folder_id=None
add_title(doc_id, "OO 디자인 컨셉")
add_subtitle(doc_id, "문서구분: 디자인 컨셉 정의서 | 작성일자: 2026년 8월 26일")
# ... add_heading / add_paragraph / add_table / add_bullet_list 위에서 아래로 ...
print(get_share_link(doc_id))
```

모든 `add_*` 호출은 문서 끝에 이어 붙으므로, 독자가 봐야 할 순서대로 호출한다.

### 7. 결과 보고

최종 산출물은 `get_share_link(doc_id)` URL이다. 사용자에게 링크를 주고, 컨셉 방향을 2~3줄로 요약해 함께 전달한다. 로컬 파일 경로가 아니다 — 존재하지 않는다.

## 문서 구조

이 형태를 사용한다. 제목 문구는 주제에 맞게 조정하되, 여섯 개 섹션은 유지한다.

```
[주제] 디자인 컨셉            (add_title)
문서구분: 디자인 컨셉 정의서 | 작성일자: YYYY년 M월 D일   (add_subtitle)

## 1. 개요                    (add_heading level=1)
   주제, 이 컨셉의 목적, 적용 대상(미정이면 "범용 — 웹/인쇄/영상 공통"), 조사 기준일

## 2. 리서치 요약             (add_heading level=1)
   컨셉 도출에 직접 쓰인 것만: 타깃, 경쟁 비주얼 경향, 색·타이포 관습, 전달할 감정·가치
   (배경 설명은 문단, 나열은 add_bullet_list)

## 3. 무드 · 톤앤매너         (add_heading level=1)
   키워드 3~5개와 각 의미·시각적 방향 (add_bullet_list 또는 add_table)
   컨셉 스테이트먼트 한 문장 (add_emphasized_paragraph)

## 4. 컬러 팔레트             (add_heading level=1)
   add_table: 색상명 | 역할 | HEX | 사용처 | 선정 근거
   사용 비율 가이드 (add_paragraph 또는 add_bullet_list)

## 5. 타이포그래피            (add_heading level=1)
   add_table: 용도(제목/본문) | 한글 폰트 | 영문 폰트 | 굵기 | 근거
   대체 폰트·사용 규칙 (add_bullet_list)

## 6. 근거 및 출처            (add_heading level=1)
   조사 출처 URL 목록, 조사 시점, 가정한 내용, 확인하지 못한 부분
```

## Windows에서 한글 텍스트 다루기

이 문서는 대부분 한글이므로, 조립 코드를 어떻게 실행하느냐가 중요하다:

- **Bash** 도구(Git Bash/MSYS)는 파이썬이 시작되기도 전에 비-ASCII 인자 문자열을 깨뜨린다. 한글이 든 인라인 `python -c "..."`를 실행해야 한다면 **PowerShell** 도구를 대신 사용한다.
- 가장 안전한 방법: **Write** 도구로 한글 리터럴(제목, 본문, 표 내용)이 들어 있는 `.py` 파일을 만들고, 그 ASCII 경로만 셸에 넘긴다. 문서가 길어질수록 이 방식이 관리하기도 쉽다.

## 하지 말아야 할 것

- 기존 지식으로 컨셉을 채우지 않는다 — 이 특정 주제에 대한 실제 조사에서 나와야 한다.
- 사용자에게 먼저 보여주지 않고 색을 확정하지 않는다.
- Drive 폴더 확인을 건너뛰지 않는다.
- 조사로부터 정당화할 수 없는 디자인 선택을 하지 않는다 — 근거를 지어내지 말고 불확실한 것은 "근거 및 출처"에 넣는다.
- 방향을 넘어 레이아웃, 그리드, 컴포넌트, 이미지 스펙까지 가지 않는다 — 그건 후속 기획자/디자이너의 일이다. 이 스킬은 팔레트, 타이포, 무드를 정한다.
- `gws` 저수준 명령이나 Docs API JSON을 직접 짜지 않는다 — `gws_docs_builder.py`를 사용한다.
- 결과는 한국어로 보고한다.
